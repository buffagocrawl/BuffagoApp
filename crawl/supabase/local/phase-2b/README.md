# Phase 2B local database foundation

This directory is a staging area for isolated development only. The SQL here is intentionally **not** under `supabase/migrations/`, is not included in the historical migration-integrity inventory, and has not been applied to Supabase production.

The foundation assumes the existing Buffago baseline provides:

- `auth.users`, `auth.uid()`, `auth.jwt()`, and the `anon`, `authenticated`, and `service_role` database roles;
- authenticated identities compatible with `auth.users`;
- `public.destinations`;
- `public.destination_ratings(id, user_id, destination_id, weight_score)`, including its existing crawl identity and rating-entry RPC contracts;
- `public.wing_media_submissions` with the approved/public-photo fields used by the gallery eligibility boundary; and
- `storage.objects(bucket_id, name, archived_at, is_delete_marker)` with reviewed active-object/versioning semantics.

The local fixtures supply reduced versions of these prerequisites. They do not certify a clean replay of the historical migration chain or live Supabase RLS.

Rating mutations acquire shared user/destination advisory locks before INSERT, UPDATE, or DELETE. Reassignment locks both old and new identities in order. AFTER INSERT/UPDATE removes Want to Try for the new rating identity; AFTER UPDATE/DELETE removes a Favorite for the old identity only when no other personal rating remains. Existing Home, Crawls, Buffacoin, and onboarding callers still persist through `destination_ratings`. Cleanup rolls back with a failed rating transaction. The canonical schema has no separate rating-withdrawal column; any future soft-withdrawal path needs equivalent authoritative cleanup.

Feature table grants explicitly remove inherited client and service-role rights before granting required operations. RLS restricts private list/vote rows to their real authenticated owner and denies anonymous-auth identities. The service role has SELECT only on the four new tables. Verdict UPDATE and direct DELETE are denied even to privileged callers; auth-user deletion cascades are allowed and decrement separate Jury counts. INSERT uses atomic counter increments instead of a snapshot-sensitive recount. Existing gallery votes/counts and rating RPC definitions are unchanged.

Three public RPCs permit service-role EXECUTE only: `is_public_wing_jury_photo(p_submission_id uuid)` rechecks approved canonical media and active storage metadata; `wing_jury_restaurant_rating_summary(p_destination_id uuid)` returns all-history `average_weight_score` and `rating_count`, excluding null scores; `wing_jury_feed_candidates(...)` orders eligible photos across the complete destination/photo catalog before applying its maximum 120-row result limit. Located discovery uses global great-circle distance followed by destination, microsecond timestamp and photo identity; unknown/invalid coordinates form a final tier. No-location discovery retains the complete catalog with deterministic destination/time/photo ordering. Keyset cursors preserve the null-distance tier and six-digit timestamp precision. There is no 250-destination/500-photo discovery cap. Guest judged exclusions are bounded to 500 ids; signed-in exclusions read the caller's committed Jury votes. Clients cannot execute these wrappers or mutate counters. The private eligibility helper remains callable by authenticated RLS evaluation without exposing the private schema. Vote validation locks existing photo and storage metadata rows while eligibility and vote counts commit together.

Run `node --test tests/database/phase-2b-local-foundation.test.mjs tests/database/phase-7b-readiness-findings.test.mjs` from `crawl/`. The 19 acceptance tests retain the original seven foundation assertions and add twelve regressions, including all-history aggregates, production-style table/function defaults, exact role privileges, account cascades, anonymous-auth privacy, rating reassignment/rollback, and fixed-snapshot isolation rejection.

Collection inserts and rating mutations require READ COMMITTED isolation. The shared lock helper rejects other isolation levels with SQLSTATE `25001` and `saved_destination_invariants_require_read_committed`, before any affected mutation; callers must roll back and retry the transaction at READ COMMITTED. Ordering a single rating's two identities does not prevent every multirow or multi-statement deadlock; an aborted transaction must be retried as a whole. A single PGlite engine's queued promises do not establish cross-session behavior. Existing-row metadata locks do not certify Storage version insertion, signing/fetchability, withdrawal after signing, or the actual REST/Edge runtime.

The Phase 7B.2.5 real PostgreSQL runner is separate from the historical `database-runtime-harness.mjs`, which still requires the missing authoritative `buffago-baseline-v1.json`. From `crawl/`, run:

```powershell
node --test tests/database/phase7b25-postgres-integration.test.mjs
```

The runner requires Windows Docker Desktop's existing `desktop-linux` context and a **cached** `postgres:17.6` image. It pins that context on every command, validates its local Windows named-pipe endpoint, rejects remote/alternate environment overrides, uses `--pull never`, and creates a uniquely named labelled container with `--network none`, no published ports and tmpfs data. Before prerequisite or foundation DDL, it verifies the container label, cached image identity, network, port bindings, mount, database, user and server version. It accepts no database URL, existing container, project link, migration history or remote host. No installation, global Docker context change, historical replay, reset, push or cleanup is performed. Existing Supabase containers are untouched. If Docker Desktop is stopped, start the installed application with `Start-Process -FilePath 'C:\Program Files\Docker\Docker\Docker Desktop.exe' -WindowStyle Hidden`, wait for its engine, and retry; a missing cached image is a prerequisite requiring separate authorization, not an automatic pull.

Each test receives a fresh synthetic database in the dedicated container. The fixture includes reduced prerequisite relations, baseline-style inherited defaults, real PostgreSQL `anon`/`authenticated`/BYPASSRLS `service_role` roles, owner RLS on synthetic ratings, and JWT claims supplied through session GUCs. These claims test SQL authorization predicates; they are not cryptographically verified Auth tokens. The staged SQL is applied directly, outside the migration queue. Every race uses distinct `psql` backend connections plus an observer which confirms `pg_blocking_pids()` before releasing the holder. The suite covers rating/list eligibility and rollback, multi-rating final cleanup, ownership/guest/anonymous denial, immutable -1/0/+1 verdicts, original conflicting verdict preservation, exact counters and unchanged gallery state, default/helper ACLs and fixed search paths, rating/save/Favorite/reassignment races, same/distinct-user votes, account cascades, photo withdrawal, existing-object archival, unsupported isolation, and a real multi-statement deadlock with whole-transaction retry.

Discovery checks use 1,003 synthetic destinations (including 300 closer destinations with no eligible photo) and 702 eligible photos, prove complete multi-page traversal beyond the former caps, retain unknown coordinates, cross the antimeridian, validate keyset precision/bounds, enforce service-only execution, and exclude judged/committed votes. A separate aggregate check supplies 1,002 ratings to verify all-history scores. PostgreSQL typed JSON parsing rejects null, nonnumeric strings, booleans, fractions and out-of-range verdicts; numeric strings such as `"1"` remain compatible with typed SQL input. Strict original JSON types are enforced by the Edge handler. This is not an HTTP PostgREST coercion test.

The plan check runs `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` on the **current RPC's extracted query body**, located and no-location discovery, owner list access under authenticated RLS, rating eligibility and active Storage lookup. Query-plan timings and node/index choices are emitted with the test results. The RPC's 120-row result bound does not bound the underlying catalog scan, eligibility function calls or global distance sort; the Edge's candidate/signing ceiling may still require repeated catalog scans. Small synthetic plans do not establish production latency or scalability, nor justify an additional production index by themselves.

The runner deliberately retains each dedicated container and logs its name, cached image id, transport and lifecycle. **Tmpfs fixture data exists only while that container remains running; stopping it loses the data.** Re-running creates another isolated container. Logs and PID/lock evidence can be redirected under the ignored `.expo/` directory. Actual Supabase Auth/PostgREST/gateway/Deno/Storage signing, Storage version insertion, native acceptance, production-scale plans and the historical baseline remain separate release prerequisites.

Before any release migration is created, this staged SQL requires review against the reconciled production catalog, a disposable PostgreSQL/Supabase runtime, and a separately authorized migration plan.

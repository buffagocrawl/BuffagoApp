# Wingdex photo vote eligibility migration

`20261008232910_wing_photo_vote_gallery_eligibility.sql` is required because the deployed `private.validate_wing_media_photo_vote()` trigger checked only authenticated user identity, `media_type = 'photo'`, and `status = 'approved'`. A direct database request could therefore vote on an approved photo whose owner was deleted, consent was invalid, or processed image was unavailable. The existing counter trigger also recounted without a per-submission serialization lock, so simultaneous different-user votes could leave stale aggregate counts.

The migration replaces the two existing private trigger functions without changing table structure, policies, grants, or the private Storage bucket. INSERT/UPDATE votes now require a permanent authenticated user and the same consent, owner, withdrawal, status, and canonical processed-object eligibility as the public gallery. The processed path must be `processed/<submission-id>/primary`; an original or another photo's derivative cannot qualify. Vote identity cannot be reassigned on UPDATE. DELETE remains available after a photo becomes ineligible. Counter recounts take a per-submission transaction advisory lock before reading votes, and the row UPDATE rechecks eligibility after any concurrent moderation update. The gallery requires a successfully signed processed image; thumbnails remain its preview asset.

The photo vote migration `20261008144550` is present in the production migration ledger but its source is absent from this checkout, which has broader historical ledger/file mismatches. This migration was created locally with `supabase migration new`; do not use a broad `db push`, `migration repair`, or reapply historical migrations. Review and apply only the target migration in a separately authorized release procedure. It has **not** been applied to production.

Local validation: `tests/wingdex-photo-vote-postgres.test.mjs` executes the migration against PGlite and checks vote transitions, persisted counts, anonymous users, forged identities, ineligible photos, missing and noncanonical processed objects, and deletion of an old vote. Its additional isolated RLS scenario installs representative catalog-reviewed own-user policies and checks cross-account reads/updates/deletes, anonymous role grants, duplicate upserts, immutable ownership, withdrawal and removal. These fixtures do not certify production policy execution. `tests/wingdex-photo-server.test.mjs` checks gallery alignment. True two-session concurrency and a two-account live smoke remain release gates; PGlite's single in-process session does not prove cross-session locking behavior. Docker's engine and a local PostgreSQL server are unavailable on this host.

## Verified production contract

- Gallery version 2 is active with `verify_jwt=false`. An unauthenticated POST works; public gallery access must remain available. Voting is a separate authenticated database operation.
- A read-only request for an existing photo destination returned `picture_count=1` and image fields `submission_id,signed_url`. `include_covers=true` without `include_images` returned no images. A viewer request using `submission_id` without `include_images` also returned no images. The prepared function adds both modes and the counters, destination, media type, approval status, creation timestamp, and expiry required by the client.
- The live `get_wing_public_gallery` RPC checks object existence in `storage.objects`, chooses thumbnail then processed then original, allows approved and publishing statuses, and orders by creation time descending then ID. These legacy behaviors explain why the new client cannot rely on the deployed function.
- The prepared function intentionally narrows moderation eligibility to approved photos with a processed path, excludes originals, and orders by likes descending, dislikes ascending, creation time ascending, ID ascending. The client uses the same ranking; response `submission_id` supplies the ID tie-breaker.
- `wing_media_photo_votes` has primary key `(submission_id,user_id)`, UUID foreign keys, and a smallint vote constrained to -1 or 1. Authenticated users have SELECT/INSERT/UPDATE/DELETE grants; RLS is enabled with own-user SELECT, INSERT, UPDATE (both USING and WITH CHECK), and DELETE policies. These match the client reads, composite upsert, and filtered delete.
- BEFORE INSERT/UPDATE trigger validates authenticated identity, photo media type, and approved status. AFTER INSERT/UPDATE/DELETE trigger recomputes aggregate counters. `like_count` and `dislike_count` are non-null integers defaulting to zero; `created_at` is non-null timestamptz. A read-only reconciliation found zero stored-counter mismatches.
- The `wing-submissions` bucket remains private. Existing storage policies provide no public read of this bucket. The prepared function uses only server-side service-role access, database-derived asset paths, five-minute signed URLs, and thumbnail-to-processed fallback; no original path or moderation metadata is emitted. No storage policy or authorization configuration changes are proposed.

## Remaining blockers / mismatches

1. **Storage existence and cover fallback — locally resolved.** The function retrieves approved photo metadata, validates each canonical processed asset, then selects covers and paginates the usable sequence. It signs canonical thumbnails only for the selected cover or page and falls back to that same photo's processed derivative when its thumbnail is unavailable. A thumbnail alone cannot make a photo displayable. `picture_count` is displayable photos; additive `approved_submission_count` counts eligible approvals, including original-only approvals. The helper exposes these as `count` and `approvedSubmissionCount` (null when an older server omits the new field). Count-only requests also validate processed assets. Empty results have count zero and images `[]`. Full-photo requests require the selected processed object and never substitute another submission or an original. Ranking, approval checks, private bucket, server-only access, and 300-second signing remain intact. Storage service failures return 503 rather than a false empty gallery.
2. **Live source comparison — investigated, unresolved retrieval.** Metadata again identifies ACTIVE version 2, ID `404ba677-8b30-45c9-b167-68f9fbbc3cba`, `verify_jwt=false`, updated epoch-ms `1791374771017`, with version-2 entrypoint `source/supabase/functions/wing-public-gallery/index.ts`. The metadata does not provide a bundle hash. Another connector retrieval failed with an internal ProtocolError. CLI 2.107.0 download in a fresh system-temp directory, without `--use-api`, also failed with `expected multipart response, got application/octet-stream`; the earlier isolated `--use-api` attempt failed identically. The last repository implementation is commit `74182f0` (2026-10-07, “Pic fix”), preceded by `4182358` (2026-08-04). Its RPC-based implementation matches the live observations, but it is a comparison baseline, **not proven deployed source**. Fresh anonymous POST probes confirm `include_images=true` returns image fields `submission_id,signed_url`; cover-only and submission-only requests return counts with no images field. The prepared handler preserves POST/OPTIONS, public access, outer response, destination IDs, 60-image paging, private Storage and signing duration, but adds covers/viewer modes, metadata/counters and approved count, changes ranking, narrows statuses to approved, and removes original fallback. Original-only and publishing-status compatibility are material differences. Obtain the actual version-2 bundle/source through a working dashboard export or Management API/CLI path and compare error handling, headers, inputs and signing before deployment. Do not identify a Git revision as deployed merely because responses match.
3. **Existing photos — root cause established; production recovery remains manual.** All 15 approved production photos were created October 7–8, not old imported legacy assets: 14 profile uploads and one rating upload. Every row has an existing original, null processed and thumbnail paths, zero processing jobs, an initial `upload_finalized_for_review` transition directly to `in_review`, then `mango_habanero_review` approval. No matching primary/other `processed/<submission-id>/...` objects were found in Storage. The live `finalize_wing_submission_upload` deliberately returns `processing_job_id=null` and does not enqueue processing. The submission table has no enqueue-processing trigger. The live `mango_review_wing_submission` requires the original and records derivative readiness but permits approval without derivatives or a succeeded processing job; it reports `processing_pending` without scheduling a job. This is the established review-first contract, also present in repository migrations `20260731013034_wing_review_only_finalization.sql`, `20260731020000_wing_review_queue_processing_reconciliation.sql` and `20260730233913_wing_review_intake_lifecycle.sql`. It supersedes the older processing-before-approval migration; null paths are expected under that workflow, not evidence of failed processing or missing path backfills. The legacy gallery explicitly displays approved originals. Deploying processed-only eligibility now would hide all 15 photos.

### Safest recovery / manual release gates

- Retain the current production gallery until the review-first/derivative-only product contracts are reconciled. Do not manufacture paths, copy originals into derivative locations, loosen moderation, or bulk update approvals to make the gallery test pass.
- For derivative-only release, first design and validate an audited processing path in an isolated non-production project using normal reserve → stage → validate → promote → finalize → review. Confirm the worker actually produces derivatives, writes paths only after successful private Storage uploads, and keeps human approval authoritative. Simply uploading/approving two more photos on current production cannot produce usable processed fixtures. The real PostgreSQL integration fixture added here follows existing finalize and approval RPCs and reproduces the original-only incompatibility; no production fixtures were created.
- Existing `repair_stranded_wing_submission` is **not safe to run blindly**: the actual live definition clears approval and priority, changes status to processing and calls `ensure_wing_processing_job`, but lacks the older migration's publishing-start guards and explicit audit records. It would require a separately reviewed, authorized recovery with publishing checks, audit/backup, a single canary, successful worker execution, re-review, then gradual expansion. Prefer a reviewed derivative backfill that preserves documented human approvals and audits each transition over silently resetting all 15 records. No recovery RPC was executed.
- Retrieve/compare the exact deployed gallery source; explicitly resolve exclusion of original-only and publishing-status photos; validate two approved processed fixtures and two-account voting in non-production. A future production rollout must include the existing two-account plan below and monitoring for gallery/signing latency. These gates require operational/product decisions and production changes outside this request's authorization.

### Batching and performance

Exact displayable counts without adding a database RPC require checking every candidate processed asset, including count-only requests. Metadata remains paged at 1,000 and signing is batched at 100 paths. Thumbnail signing is limited to the selected cover or 60-photo page. The 1,001-photo cover regression signs 1,001 processed paths plus one thumbnail in 12 batches. The 250-destination/two-photo cover regression signs 500 processed paths and 250 selected thumbnails in eight batches. Only selected image URLs leave the boundary; non-selected processed signs establish the displayable count. Measure latency with real non-production volumes before release. If excessive, use a separately reviewed service-only existence/count RPC. Eligibility is a request-time snapshot; deletion after signing may still cause an image load failure.

Read-only catalog inspection verifies schema compatibility, not authenticated mutation behavior. The updated endpoint, real voting, persistence, and cross-account cover changes remain unverified until deployment and the smoke test below. Concurrent votes should also be checked against the stored counters; local SDK mocks do not exercise production trigger transaction behavior.

## Two-account end-to-end plan after approved deployment

Use two real authenticated accounts A and B in separate sessions/devices and a test restaurant with at least two approved photos P and Q with existing processed objects. Record baseline votes/counters and creation timestamps/IDs; use comparable counts so two accounts can change the winner. Keep pending/rejected/withdrawn/video fixtures for negative checks, managed only through existing moderation tools.

1. Fetch covers, gallery pages, and P's full-photo response. Confirm only eligible photos, correct count, all required fields, thumbnail gallery URLs, processed viewer URLs, and five-minute expiry. Check returned counters against a read-only aggregation of votes. Check the ranking on both Wingdex routes: likes descending, dislikes ascending, earliest creation, lowest ID.
2. A likes P: exactly one `(P,A)` row with vote 1, likes increase by one, and A's selected control persists after closing/reopening the viewer. B sees the same totals after refresh while B's selection remains empty.
3. A taps Like again: row removed and likes return to baseline. Test dislike, removing dislike, and both switching directions. Confirm one row per user/photo and correct counter deltas for every transition. Rapid double taps must not duplicate writes; offline failure must roll back the optimistic UI and permit retry.
4. A and B vote to make Q outrank P. Refresh both Wingdex routes and verify Q becomes the cover for both accounts. Verify fewer dislikes wins a likes tie, then date/ID resolve equal totals. Votes should affect photos only, leaving restaurant scores and ratings unchanged. Allow the 30-second response cache to expire and explicitly refresh when checking cross-account changes; passive cover refresh is approximately four minutes.
5. Restart both apps and sign out/in. Confirm persisted totals and each account's own choice. Switch accounts on one device and verify selections change without leaking the previous account's vote state.
6. Submit votes on the same photo nearly simultaneously from A and B; reconcile actual rows and both counters after both requests complete. Repeat removal/switch operations and verify no lost aggregate updates.
7. Through existing moderation, withdraw/reject a voted photo. Refresh gallery/cover and request its full photo: it must disappear and must no longer receive a new/switch vote. Pending/processing/publishing-status photos and videos must never become covers or receive votes. Approval with a valid processed object makes a photo eligible. A previously issued signed URL may remain usable until expiry; fresh requests must enforce moderation.
8. Attempt to read or mutate A's vote as B and to forge `user_id=A` in B's request. Reads must not disclose A's rows and mutations must not succeed. Guest browsing remains available; guests cannot vote. Direct anonymous/authenticated bucket listing or original/processed object reads without a signed URL must stay denied. Never include privileged keys in client requests.
9. Validate missing thumbnail fallback, missing winner/runner-up handling after the fix, expired URLs and refresh, withdrawn/deleted full-photo errors, pagination beyond 60 images, and empty galleries. Restore A/B test votes to their baseline and recheck counters.

| S-01 | High | Staged SQL revokes table rights from PUBLIC/anon but never from authenticated before narrow grants. The production catalog reviewer reports postgres/public default relation ACLs grant ALL to authenticated, anon, and service_role. Applying this SQL retains authenticated UPDATE, DELETE, TRUNCATE and other unintended rights. The old fixture has no such defaults. | Explicitly normalize ACLs to the intended rights and verify effective privileges under representative existing/default grants. No UPDATE/DELETE policy currently permits an ordinary vote REST mutation, but excess grants are still present. TRUNCATE bypasses RLS; this report does not claim PostgREST exposes a truncate route. | S-02 | High | Want to Try cleanup handles only `AFTER INSERT`. ## Other implementation limits

- Feed retrieval considers at most the first 250 destinations and first 500 oldest photo candidates. Repeated cursors rescan the same bounded set; reaching its end can report exhaustion while eligible photos exist beyond the cap. Distance ranking occurs only inside this selected set. Define intentional coverage and test >250 destinations/>500 photos before claiming complete proximity discovery.
- Reveal calculates a mean of at most the newest 1000 rating rows (`wing-jury-reveal/index.ts:26`). It is not necessarily the canonical all-history Wingdex average, and Number(null) can count a missing score as zero. Use/verify the established rating aggregate and qualifying-score semantics. The existing social opt-out migration explicitly retains opted-out scores in restaurant aggregates, so including those scores alone is not a privacy finding; individual other-user rating identities are not returned.
- Guest reveal's `guest_verdict_registered=true` is forgeable session-local UI state. This is acceptable only under the documented public guest-reveal contract; it cannot serve as an authorization proof for any private data or write. Invalid/missing bearer callers degrade to guest for public handlers; vote still returns 401.
- All handlers answer OPTIONS with wildcard origin and authorized request-header names, reject non-POST with 405, and return bounded controlled JSON error codes without database messages/secrets. No credentialed cookie CORS is enabled. A real browser-to-gateway preflight check remains outstanding; Access-Control-Allow-Methods is not explicit. `private, max-age=30` response caching should be reviewed for personal reveal; explicit no-store avoids retained account-specific responses.
- Service-role secrets appear only as server environment names in the shared handler. A focused source test asserts absence of `SUPABASE_SERVICE_ROLE`, `service_role`, and `sb_secret_` references in six public entry files: Jury service/component/route, saved-list service/hook, and feature configuration. This checks those references, not every possible hardcoded secret in the repository. Supabase JS Edge import is pinned to 2.58.0. Network responses deliberately project safe fields instead of serializing privileged query rows. No secrets were read, added, or logged by this review.
- No new rating, wallet, gallery vote, mission reward, social visibility, or upload mutation was introduced. The database cleanup trigger covers canonical rating INSERT from Home, Crawl, Buffacoin, and onboarding replay; successful score upsert UPDATE does not become cleanup coverage merely because its caller mentions destination_ratings.

## Release sequence

1. Reconcile Phase 2A applied history and production catalog without rewriting historical migration bytes or treating current file checksums as deployed evidence.
2. Separately authorize and implement the staged security/lifecycle/guest fixes, convert TODO regressions into ordinary passing tests, and add genuine two-session race tests in a disposable PostgreSQL/Supabase environment.
3. Create and review the additive migration only after catalog reconciliation. Inspect exact effective privileges, RLS, SECURITY DEFINER paths/EXECUTE, existing baseline policies, and account-deletion behavior in that runtime.
4. Apply the reviewed migration, then deploy the compatible three handlers plus reviewed JWT configuration/secrets under explicit release authorization. Schema must exist before handlers are made available; clients remain disabled throughout.
5. Verify signed-out/public reads, authenticated/anonymous denial, all rating completion paths, cross-account boundaries, concurrent duplicates, canonical signed media, and mobile/browser transitions against the integrated runtime before enabling either flag. Keep production defaults false until these checks pass.

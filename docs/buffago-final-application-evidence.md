## Reviewed contracts

- Rating retries are bounded to three whole-RPC attempts for `40P01`/`40001`, with copied stable inputs and operation IDs, and a pinned original bearer token. Authorization, generic uniqueness errors, thrown network errors, and unknown COMMIT outcomes are not automatically retried. A later deliberate same-operation receipt request is the supported recovery route. The PostgreSQL evidence separately verifies supported `23505` receipt recovery; a uniqueness exception is never generalized into a retry policy.
- Permanent Jury writes derive the user from `auth.getUser`, reject guest/anonymous users, use the caller-scoped anon-key client, and let database RLS enforce ownership. The service-role client performs narrowly scoped eligibility/read operations. Duplicate user/photo verdicts return the prior immutable verdict, including conflicting requests; neutral/-1/+1 are strict numeric values. Count-read failure after a committed vote is safely recoverable through a later immutable duplicate lookup.
- Guests record verdicts only in the in-memory session, and persistent guest exclusion hints are capped at 500 while the full local session filters response photos. Guest reveal uses the established Boolean session-verdict signal; it is an application experience boundary, **not cryptographic proof that a guest viewed/voted on the photo**. Restaurant identities are intentionally public after that signal; private ratings/saved lists require the verified authenticated account and committed vote. Invalid tokens cannot obtain another account's private state. Owner acceptance of this existing guest reveal contract must not be misrepresented as a stronger security guarantee.
- Gallery likes/dislikes and Jury verdict counts use separate tables/contracts. Feed signing rereads eligibility, and existing database policies prevent a withdrawn photo from accepting a new Jury verdict. A previously issued five-minute signed URL is a bearer capability; immediate revocation after withdrawal is a live Storage behavior check, not a local guarantee.
- No new FK, unlink, retention, or account-deletion semantics were introduced. A linked media `rating_id` RESTRICT may still prevent Auth deletion. A terminal failed manifest has no supported RPC reset/recovery; the candidate now preserves it and returns an operator-recovery requirement. Approving a recovery procedure and validating deployed correspondence remain external release gates. **Independent review additionally identified the existing upload/deletion race:** uploads after prepare can leave private objects outside the manifest. A controlled regression inserts a new owned media row during Storage cleanup and verifies the final reread blocks Auth deletion and subsequent automatic retry. This is defense in depth, not an atomic fence. Approve and prove a media-write freeze covering reservation/finalization RPCs, direct Data API, upload Edge endpoints and Storage through Auth deletion, or approve a separately versioned atomic backend correction. No production account-deletion success claim is made without that prerequisite.

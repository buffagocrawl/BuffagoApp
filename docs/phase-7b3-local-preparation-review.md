## Review against staged SQL

The staged file remains unchanged at `crawl/supabase/local/phase-2b/20261009_local_phase2b_foundation.sql`: four tables, fourteen functions, nine triggers, nine policies, six explicit indexes. It uses convenience replacements/drops and implicit ownership, so it is not a release migration.

Permissions: explicit new-table revokes prevent inherited broad defaults from granting UPDATE/TRIGGER paths; authenticated collections retain SELECT/INSERT/DELETE, votes SELECT/INSERT, counts SELECT. Service role gets only intended reads/wrappers; caller JWT performs votes. The current direct-DML architecture is protected by ownership/eligibility triggers, rather than the discovery proposal's RPC-only mutation architecture. No new RPC is necessary merely to match old prose. New-table RLS does not change the existing `TO PUBLIC USING true` rating policy. Jury reveal can enforce its own response boundary but cannot promise product-wide blind rating secrecy. Existing broad table TRIGGER grants also merit a separate reachability review: RLS is a row policy, not a replacement for DDL/trigger privileges. No baseline ACL was changed here.

Deletion: the staged media vote FK RESTRICT retains voted media; existing moderation/job/reward restrictions do not prove every currently allowed media hard-delete is already blocked. Withdrawing/pseudonymizing media makes it ineligible but preserves votes. Adopting this additional retention restriction still needs an explicit supported deletion contract. Existing media rating RESTRICT can block final-rating deletion and auth deletion via rating CASCADE, even without Jury. Failed deletes must roll back collection/count changes; do not fix existing account deletion by loosening media FKs. Media owner SET NULL requires the existing pseudonymization trigger; local candidate sets owner_deleted_at and refuses reidentification. Jury's account-delete exception permits vote deletion only after auth identity disappears. Full supported account-delete orchestration remains unverified.

Trigger order: PostgreSQL executes same-event triggers in name order. The new `destination_ratings_lock_collection_identities` BEFORE trigger sorts before `guard_buffacoin_rating_writes`. Local guard candidate only checks the atomic-write GUC and returns NEW; it does not change identity or acquire a lock. The friend-notification AFTER trigger sorts before Want cleanup; `trg_rating_after_insert` sorts after it. An existing AFTER failure rolls back rating and cleanup together, but unknown reward/notification dependencies may observe different list state or acquire conflicting locks. Preserving names alone cannot establish coexistence.

Local source candidates inspected: guard in `20260729153000_serrano_trust_repair.sql`, friend notification in `20260724012000_daily_engagement_notifications.sql`, owner pseudonymization in `20260729121000_wing_shots_security_rpc.sql`.
